# 故障对照表：症状 → 根因 → 修法

出问题时先查这里。每一条都是实操中真实踩过并修好的。

## 画面污染

### 整段录像左上角有一条黑色标题栏，内容是文件路径 / `cmd.exe` / `Xshell`

**根因**：录制期间技能执行了会弹出控制台的命令。那个窗口正好落在用户的采集屏上，
被一起录了进去。

**修法**：两层防护。

1. **命令本身无窗口**：技能内部的每个子进程都带 `CREATE_NO_WINDOW`（0x08000000）。
   控制台程序在没有父控制台时默认会**新建一个可见窗口**，这个标志阻止它。
   从外部 shell 调用技能时用 `scripts/h.ps1`，它以 `CreateNoWindow` 启动子进程。
2. **守卫兜底**：录制前 `studio guard start`，它每 0.25 秒扫一遍窗口列表，
   把新出现的控制台窗口和输入法 / 通知浮层立刻 `SW_HIDE`。

**判据**：`studio guard status` 报「no console-like window on the capture display」，
并且成片的逐帧 OCR 审计没有命中控制台。

### 守卫把用户正在看的窗口藏起来了

**根因**：`--protect` 没有传正在演示的程序（按标题匹配）。

**修法**：把目标程序的标题加进去，例如
`studio guard start --project <项目> --protect "Chrome" --protect "Blender"`。

### 守卫藏掉了另一块显示器上的窗口

**根因**：旧判据只算「有没有压到」，一块屏上的窗口可能只压到采集区几像素。

**修法**：现在的判据要求**真实重叠**（交集至少 120×90 像素），
只擦边的窗口不会被误藏。

### 画面右下角浮着一个「YouTube / 推荐视频 / For you:」气泡

**根因**：浏览器通知。Chrome 的通知会长期挂在右下角，正好压住产品面板。

**修法**：
1. **预防**——把浏览器 profile 的通知关掉。在 `Preferences` 里设
   `profile.default_content_setting_values.notifications = 2`。
2. **补救**——审计会报出精确时间码，把受影响的 `in`/`out` 挪到干净区间，或补录那一段。
   通知气泡通常一次挂几分钟，不是几秒。

### 点「下载」「保存」之后浮出一个启动页 / 偏好设置对话框

**根因**：应用首次启动的欢迎页或首启向导。

**修法**：逐帧扫一遍源片段，找出对话框消失的秒数，用那之后的区间。
`studio audit` 会报出来，但这类往往只在源片某一段出现，需要单独确认边界。

### 画面里有白色/灰色的圆点或小方块（Blender 的指针样式）

**根因**：这是 Blender 自己的视图叠加层，不是外来窗口。**不要**当污染处理。

**判据**：审计的正则是针对文本的（控制台路径、通知标题、启动页文案）。纯图形叠加层不会被 OCR 命中。

### 输入法窗口（Windows 输入体验）盖满整屏

**根因**：中文输入法候选窗是独立的顶层窗口。

**修法**：`studio prep` 会把它藏起来。它类名是 `IME`，在采集区内，优先隐藏。

## 音画不同步

### 口播跑在画面前面，越到后面偏得越多

**根因**：章节画面总长 ≠ 口播总长。常见原因是素材不够，按顺序截取时后面的镜头被整段砍掉。

**修法**：用**按句绑定**而不是按时长均分。`plan.json` 里给每个 beat 写 `seg`（第几句口播），
构建器会把这句的实测时长精确分配给它；素材不够时用 `tpad` 补最后一帧。
`studio verify --expect-duration` 可以把漂移量化成一个数字。

### 某一章画面明显比其它章短

**根因**：该章的 beat 自然长度之和短于口播长度。

**修法**：构建器会自动补帧并把章节对齐到口播长度。检查 `studio build` 输出里
`XXs (narration YYs)` 两行是否相等。

## 配音

### 某一两句明显拖沓，像被拉慢了

**根因**：TTS 对某段文本生成异常（音频里带了长静音）。

**判据**：`studio voice` 输出的 `chars/s`。连续段落正常值约 4.5–6.5 字/秒；
**低于 3.0 就是异常**。

**修法**：改写该句（通常改标点或断句即可），重跑 `studio voice`。
TTS 按「id+文本哈希」缓存，只有改动的段会重新合成。

### 配音念的数字和屏幕上的不一样

**根因**：口播稿里的数字是凭记忆写的。

**修法**：从真实界面读到数字再写稿。改稿后必须重跑 `studio voice`——
段落文本变了，时长也会变，`plan.json` 里的 `seg` 绑定会自动跟上。

## 构建失败

### `Error applying option 'eval' to filter 'crop'`

**根因**：这个 ffmpeg 构建的 `crop` 没有 `eval=frame`，不能做逐帧变化的推近。

**修法**：用静态推近（`crop` + `scale` 固定比例）。`build.py` 的 `zoom_filter()` 已经这么做了。

### `First input link main parameters (size 1920x1080) do not match ... (size 1600x1090)`

**根因**：参与转场的片段分辨率不一致（常见于特写片段被缩放成了非 16:9）。

**修法**：所有片段统一到 1920×1080。`build.py` 的 `cut_range()` 默认会做
`scale + pad + setsar=1` 归一化，特写素材会加黑边而不是变形。

### `x264 [error]: malloc of size ... failed`

**根因**：把十几段视频一次性丢进一条 `xfade` 滤镜链，每段都要一个解码器和帧缓冲，内存爆了。

**修法**：用**二叉树**方式两两转场。`build.py` 的 `concat_xfade()` 已经是这个结构，
任意时刻最多三路输入活着。

### `Stream specifier 'vo' in filtergraph description ... matches no streams`

**根因**：`sidechaincompress` 在这个构建上配置失败，报错信息具有误导性。

**修法**：别用 ffmpeg 的侧链压缩。`build.py` 的 `duck_bgm()` 用 numpy 按人声包络算出增益曲线，
再写出一个新的 wav，确定性且不依赖滤镜可用性。

### `libx264 ... height not divisible by 2`

**根因**：缩放后高度是奇数。

**修法**：用 `scale=1600:-2` 而不是 `-1`。

### `Error applying option 'eval' ...` / `Option not found`（别的滤镜）

**根因**：滤镜参数在当前 ffmpeg 版本上不存在。

**查法**：`ffmpeg -h filter=<名字>` 看这个构建实际支持哪些选项。

### 音轨比预期响 10 dB 或闷 10 dB

**根因**：`amix` 默认按输入数量归一化，两路输入会各降 6 dB。

**修法**：`amix=inputs=2:normalize=0`，再用 `loudnorm=I=-16:TP=-1.5:LRA=11` 统一到目标响度。
`loudnorm` 之后要补 `-ar 48000`，否则可能输出 96 kHz 的 AAC。

## 素材（来自用户的外部录制）

### 素材很模糊，文字发虚

**根因**：素材不是原生分辨率——要么录屏工具开了「缩放」或用了「优化资源」，
要么录的是整屏但源是高分屏（3840×2160 的屏录成 1920×1080）。

**修法**：让用户用录屏工具的**原始分辨率**录制，不要开降采样、不要开「硬件加速缩放」。
成片统一到 1920×1080 是剪辑阶段的事，采集阶段必须保原生。

**注意**：不要用 `studio shot` 抓的帧当素材——它走的是桌面合成，
高分屏上同样会糊。它只用来确认状态。

### 素材里出现了录屏工具自己的边框或控制条

**根因**：录屏工具在录制时显示了叠加层。

**修法**：让用户改用「无边框录制」或隐藏控制条后重录那几秒；
已经录进去的，把 `plan.json` 里对应的 `in`/`out` 挪开。

### 用户的素材打不开 / 长度为 0

**根因**：录屏工具被强杀，MP4 的 moov 没写完（部分工具写完才封口）。

**修法**：让用户用录屏工具的「正常停止」结束录制，不要直接关进程。
拿不到原文件时可以用 `ffmpeg -i in.mp4 -c copy fixed.mp4` 抢救一遍。

### 素材太长，切不动

**根因**：一次录了完整流程，几十分钟起步。

**修法**：让用户**按功能分段录制**，一次录一个功能。
必须一次录完时，靠 `studio index` 建立索引，再按索引挑区间。

### 索引里找不到某个控件

**根因**：`--step` 太大（采样太稀，正好错过了那几秒），或者画面分辨率低导致 OCR 认不出。

**修法**：对该片段用更细的步长重跑索引，例如
`studio index --project <项目> --clip rec.mp4 --step 0.5`。
仍然找不到时，直接对可疑区间做定点 OCR。

### 索引里全是乱码或空文本

**根因**：OCR 引擎内存不足（`bad allocation`），或者画面是深色主题导致对比度不足。

**修法**：关掉浏览器和多余的 ffmpeg 再跑；`index.py` 已经带重试。
采样分辨率固定为宽 1280，不要再往下降。

## 操作阶段

### 抓一帧确认状态时得到黑屏

**根因**：抓屏的 display index 不对，或目标窗口在另一块屏上。

**修法**：`studio windows` 列出所有窗口的几何位置；把目标窗口移到采集区并最大化，
确认 `shot --region` 与之匹配。

### 用户录进来一大段发呆或等待

**根因**：录制时长包含了思考、读文档、试错的过程。

**修法**：这是正常的，后期剪掉即可——用索引里的「变化点」定位真正的操作区间。
更省事的做法是下次让用户按功能分段录。

## 审计

### 审计跑到一半报 `bad allocation`

**根因**：OCR 推理在内存紧张时分配失败（常见于同时开着浏览器和多个 ffmpeg）。

**修法**：`audit.py` 已经带重试和 `gc`。另外：审计前关掉浏览器；
把审计的 `scale` 降到 1280（默认即是）；分章审计而不是一次跑完。

### 审计报了一个明明没问题的地方

**根因**：正则误命中。正则覆盖了 `通知` 这种通用词，可能命中产品自身的文案。

**修法**：看 `audit.txt` 里的具体命中串。确认是误报就收窄正则；
把误报词加入 `audit.py` 的 `PATTERNS` 排除列表，不要直接忽略整条时间码。
